## Findings

### [WARN] plugins/specclaw/bin/specclaw-azdo-pr:388-407 — Design adherence
**Problem:** `spec.md`'s Approach says to "pass [sections] to a new `fit_description` helper"; the implementation instead relies on bash's dynamic variable scoping — `fit_description`'s `for pair in timing_body:timeline.md staged_body:staged-files-report.md ...` hardcodes each shrinkable variable's *name* as a string, then reads/writes it indirectly via `body="${!var}"` and `printf -v "$var" ...`. This works (tests confirm it), but it is a real deviation from "pass them" with no comment explaining *why* implicit dynamic scoping was chosen over explicit parameters — only a comment describing the mechanism ("read through bash's dynamic scoping", line 331). It also means the coupling between `build_pr_description`'s local variable names and this string list is invisible to shellcheck: renaming `staged_body` in one place without updating line 388-389 fails silently (`${!var}` on an unset name is just empty string, so that section is quietly never considered for shrinking — no error, no test failure until someone notices the section never truncates).
**Fix:** Either add a one-line comment on the `for pair in ...` list stating this coupling is deliberate and must be kept in sync, or pass an explicit ordered list of `name:file` pairs into `fit_description` as an argument from `build_pr_description` so the coupling is visible at the call site.

### [WARN] plugins/specclaw/bin/specclaw-azdo-pr:410-417 — Correctness (FR5 edge case)
**Problem:** FR5 requires "The `**Verdict:** …` line and the `🤖 Generated by SpecClaw` footer are never removed." The hard cap only protects the footer:
```
local tail=$'\n---\n🤖 Generated by SpecClaw'
local keep=$(( max - ${#tail} ))
(( keep < 0 )) && keep=0
desc="${desc:0:keep}${tail}"
desc="${desc:0:max}"
```
If `max` is small enough that `keep` clamps to 0 (e.g. `azdo.pr_description_max: 10` — any positive integer passes the `[[ "$cfg_max" =~ ^[0-9]+$ ]] && (( 10#$cfg_max > 0 ))` check at line 325, no floor is enforced), `desc` becomes just the footer text sliced to `max` bytes, and the `**Verdict:** ...` line — which sits earlier in the string and is never separately protected — is dropped entirely. This only manifests at unrealistic budgets far below any sane ADO/config value, and FR1 (the byte cap) still holds, but it is a genuine gap against FR5's "never removed" wording, and there's no AC or test covering it.
**Fix:** Enforce a floor on `max` (e.g. reject/ignore configs below some minimum such as the fixed skeleton's length), or protect the verdict line the same way the footer is protected in the hard-cap path.

### [WARN] plugins/specclaw/bin/specclaw-azdo-pr:393-405 — Correctness (shrink can grow the string)
**Problem:** For a section whose body is already shorter than its own truncation pointer (`ptr` is `_…truncated — full text in \`.specclaw/changes/<change>/<file>\`_`, ~60-90 chars depending on `CHANGE_NAME`), the loop still replaces it once `target <= 0`:
```
target=$(( ${#body} - over - ${#ptr} - 1 ))
kept=""
if (( target > 0 )); then ...; fi
printf -v "$var" '%s%s' "$kept" "$ptr"
```
Nothing checks that `${#ptr} < ${#body}` before committing to the replacement, so a short section (e.g. a two-line `staged-files-report.md`) can end up *longer* after "shrinking," pushing more work onto lower-priority sections or the final hard cap than FR3's "each shrink stops as soon as the whole fits" implies. The final hard cap still guarantees FR1, so this is not a correctness break, just a wasted/counterproductive shrink.
**Fix:** Skip the replacement (leave the body as-is) when `${#ptr} >= ${#body}`, since truncating in that case cannot help.

### [NOTE] plugins/specclaw/bin/specclaw-azdo-pr:290,297,307 — Naming
**Problem:** The three variables `fit_description` shrinks are named inconsistently for an identical role: `test_lines` vs. `staged_body` / `timing_body`. All three are now "a shrinkable section body consumed by the `pair` list in `fit_description`," but only two carry the `_body` suffix that signals that role.
**Suggestion:** Rename `test_lines` to `test_body` (and adjust the one reference in `assemble_description`'s `test_section` heredoc at line 339) for a uniform naming convention across all three shrinkable bodies.

### [NOTE] plugins/specclaw/bin/specclaw-azdo-pr:332-420 — Complexity

Both are already well covered by `run-azdo-pr-description-tests.sh` and read as one coherent unit each, so this is a soft note rather than a real complexity problem — nesting stays at 3 levels in `fit_description` (`for` → `if` → `while`), within the stated limit.
**Suggestion:** No action required unless a future change adds another branch to either function.

### [NOTE] plugins/specclaw/bin/specclaw-azdo-pr:418 — Naming / message clarity
**Problem:** `warn "PR description was ${original} chars (limit ${max}) — truncated: ${cut[*]:-none}; ..."` names the truncated sections using internal bash variable identifiers (e.g. `test_lines`, `timing_body`) rather than the human-facing section titles used in the rendered markdown (`Tests`, `Time accounting`). FR6 asks for a warning "naming the truncated sections," which this technically satisfies, but an operator reading stderr sees implementation detail instead of the section they'd recognise from the PR body.
**Suggestion:** Map each `var` to its rendered heading (e.g. via a parallel label in the same `pair` string, `timing_body:timeline.md:Time accounting`) before joining into the warning.

### [NOTE] plugins/specclaw/bin/specclaw-azdo-pr:381 — Design adherence / documentation
**Problem:** FR7 requires character counting "under a UTF-8 locale." Nothing in `specclaw-azdo-pr` sets or checks `LC_ALL`/`LANG`; the guarantee depends entirely on the calling environment's locale. The code comment at line 381 ("a C locale counts bytes, which only ever over-counts") correctly notes this is safe for the FR1 byte-budget guarantee, but it is undocumented in the NFRs/spec that FR7's character-accuracy promise is conditional on the caller's locale, and CI/production environments with `LANG=C`/`POSIX` will silently over-truncate multi-byte content more aggressively than necessary.
**Suggestion:** No functional fix needed (the over-count direction is safe); consider noting the locale dependency in the NFR section for future maintainers, matching the disclosure already present in `run-azdo-pr-description-tests.sh`'s own locale-detection block.
